## 1. Guiding Principles

1. **Never edit historical migrations (`0001`–`0037`).**
2. **Never deploy R6.5 remediation directly to production without isolated staging/local pgTAP verification first.**
3. **Preserve 100% backward compatibility:** All function signatures (`public.*` and `famora.*`) remain unchanged; no table drops, no `CASCADE`, and no destructive backfills.

## 3. Impact & Rollback Assessment

- **Application Impact:**
  - `record_debt_payment`: UI/server action (`analytics-actions.ts`) should ensure users cannot submit an overpayment above `remainingNumeric` (already validated/clamped in UI, server will now reject cleanly with `22023`).
  - `record_finance_transaction`: Archived accounts are rejected (`22023`), matching UI intent.
- **Rollback Strategy:** Since Stage B only updates function definitions via `CREATE OR REPLACE FUNCTION` / `ALTER FUNCTION`, rollback is non-destructive: restore the prior `0015`/`0017`/`0018`/`0020`/`0024` function definitions from git or the pre-migration `pg_dump`.
